## 诊断：原型编辑器 AI 生成卡在 "Thinking Reasoning…"（仅诊断，未改代码）

- 架构结论：原型编辑器 AI 走浏览器直连模型厂商（`frontend/src/pencil/app/ai/chat/transports.ts` 的 `DirectChatTransport + ToolLoopAgent`），后端完全不参与，此类卡顿与后端/SSE 服务无关。当前模型为内置 `deepseek-v4-flash`。
- 主因：一键生成 prompt（`ChatPanel.vue` PRD_BASIS_PROMPT）要求为每个 P0 页面建独立画板，PRD 依据规范页面清单 4–10 行且每页详情具体到列名/按钮；而 `system-prompt.md` 硬约束「每次 render ≤40 元素、每屏 2–3 次、全任务 50 步（建议 12–15 步）」。二者数学冲突，推理模型在 reasoning 里反复重算拆分，长时间不发 tool call。截图 reasoning 原文「5 calls for screen 1. Too many.」即为证据。这解释了「有时候」才卡：单页简单需求可规划完，多页需求会循环。
- 放大器：`store.ts` 的 `DEFAULT_MAX_OUTPUT_TOKENS = 32768`（注释记录了 16k 时多屏请求以 `finish_reason=length` 收尾且零输出的历史 bug，仅调大阈值未解决机制）；29KB 系统提示词 + 6KB PRD 依据且 DeepSeek 链路无 prompt caching；正式链路无超时/心跳/重试（全项目仅 `connection-test.ts` 有 `AbortSignal.timeout(15_000)`），`reportDeadStep` 只在 `onStepFinish` 触发，流半开时 status 永远 streaming。
- 独立现象：Chrome「此页面没有响应」= 渲染进程主线程被同步任务占满。嫌疑：`ChatPanel.vue` 的 `watch(messages, ..., {deep:true})` + 每 delta `scrollIntoView({behavior:'smooth'})`；`tools/index.ts` onAfterExecute 的整页 Yoga 布局 + 两次 `structuredClone` 快照 + CanvasKit 重绘；`design-jsx/render.ts` 用 `new Function` 在主线程同步执行 JSX。
- 待办方向（未实施）：加 first-chunk / chunk-idle 超时与可见错误；多页面拆成按页多次 run；放宽 40 元素/50 步约束或按页切片注入依据；deep watch 节流；dead step 自动续跑而非只 toast。

## 诊断修正（用户反馈：换其他原型同样会卡）

- **修正**：案例复杂度（4–10 页面 × 40 元素 / 50 步）只是放大器，不是根因。
- **通用主因 = 浏览器直连 SSE 零兜底**：`transports.ts` 用 `DirectChatTransport`；AI SDK 的 `sendMessages` 只透传 abortSignal、无 timeout，`reconnectToStream()` 硬编码 `return null`（`ai/dist/index.js` 17511 / 17534）；`AbstractChat.makeRequest` 仅在流结束或抛错时 `setStatus(ready|error)`（17453-17465）。整个 `app/ai` 目录无 fetch 包装 / `AbortSignal.timeout` / setTimeout / chunk 日志（唯一 15s 超时在 `connection-test.ts`）。SSE 半开时：status 永远 streaming、reasoning part 永远 streaming、无 error 无 toast、`onStepFinish` 不触发、`didHitStepLimit()` 为 false 连 Continue 按钮都不出现 → 永久 Thinking，与生成内容无关。触发源是概率性外部长尾（网关无 keepalive、网络抖动、标签页节流、模型长 reasoning、CORS 代理缓冲）。
- 次级通用因素：`deepseek-v4-flash` 每步先吐 `reasoning_content`（适配器 `delta.reasoning_content` → reasoning-delta），此窗口无任何工具卡片；`ChatPanel` deep watch O(n²) + 整页 Yoga 布局 / 两次 `structuredClone` 快照 / CanvasKit 重绘 → Chrome「页面无响应」；无 prompt caching，每步 `validateUIMessages` + `convertToModelMessages` 重发全量上下文。
- 判定捷径：DevTools Network 看 `chat/completions` 是否 Pending 且 chunk 停止新增 >30–60s；Performance 看 Long Task；Copy log 看 tool call 数与 step usage。
- 最小修复建议：加 first-chunk / chunk-idle 超时 + 可见错误与重试入口；reasoning 阶段显示耗时/token 数；长期把 SSE 挪到后端代理以获得超时、心跳、重连与日志。

## 第三次修正（用户补充：短提示词 / 空白原型同样复现，且「过许久又正常」）

- 「能自愈」证伪上一轮的「半开流永久卡住」；空白「未命名原型」+ 短提示词 + 无 PRD 依据证伪案例复杂度。
- **收敛结论**：两个现象是同一根因的两个表现 —— 渲染进程主线程被同步长任务占满，SSE chunk 已到达网络层但 JS 无法 `reader.read()` 消费，任务结束后缓冲数据被批量处理即自愈。与提示词、PRD、画布内容均无关。
- 主线程热点（已亲自核对行号）：
  * `frontend/src/pencil/components/EditorCanvas.vue:54,58` **两次 `useCanvas`** → 两条 `kit-loader.ts:39` `await loadFonts()` 链路；`renderer/fonts.ts:80-82` 每条新建 TypefaceFontProvider，`fonts.ts:75-88` `attachProvider` 对已缓存字体逐个重注册 + `applyIfReady()`。

  * `frontend/public/canvaskit.wasm` 7.09MB（`canvaskit.ts:24` ← `kit-loader.ts:32`）；kiwi `prefetchFigmaSchema`（`editor/create.ts:65` → `fig/codec.ts:43` → `schema-runtime/js.ts:337` `new Function` 编译 119KB / 605 定义的 fig.kiwi）。
  * 生成期持续层：`ChatPanel.vue:82` deep watch + 每 delta `scrollIntoView({behavior:'smooth'})`；AI SDK 每 chunk `replaceMessage` + reasoning `<p>` 整段文本替换，累积 O(n²)，reasoning 结束即自愈。

## 实验 1 结果与首次修复（分支 fix/prototype-ai-stream-hang）

- 用户结果：空等 30–60s 后发短提示词**仍卡**，且 Thinking 框空白（连第一行 reasoning 都没渲染）→ 按前一轮判定规则锁定「生成期流式渲染」，主线程从流一开始就被饿死。注意实验 1 只排除了 <60s 的挂载开销，若字体注册本身耗时 >60s 仍可能撞上，待 Performance 确认。
- 首次改动（仅 `frontend/src/pencil/components/ChatPanel.vue`）：
  * 移除 `watch(messages, scrollToBottom, { deep: true })`，改为监听 `contentFingerprint`（消息数 / 末条 parts 数 / 末尾文本长度的轻量字符串指纹）与 `status` 的组合；
  * `scrollToBottom` 用 `requestAnimationFrame` 合并为每帧一次，`behavior: "smooth"` → `"auto"`，消除每 delta 重启动画与强制 layout；
  * 新增 `onBeforeUnmount` 取消挂起 rAF，移除不再使用的 `nextTick` import。
  * 机制：AI SDK `SerialJobExecutor` 每 chunk 一个微任务 + Vue deep traverse + nextTick + smooth scroll，微任务队列持续不空 → 输入与渲染被饿死 → Chrome「页面无响应」；流结束后队列排空即自愈。
- 验证：`pnpm --filter frontend typecheck:pencil` 有大量**既有**错误（`~icons/*` 声明、storybook、路径别名等），但 grep ChatPanel 无新增错误。
- 待办：若 HMR 后仍卡，需 DevTools Performance 录 5–10s 看 Long Task 栈顶，再决定是否处理「CJK 字体重复注册」层（EditorCanvas 两次 useCanvas → 32–40 次 1.09MB registerFont）以及流空闲超时兜底。

## 新增功能：Thinking 内容区边思考边自动向下滚动

- 需求背景：截图里 reasoning 框内部的 `max-h-40 overflow-y-auto` 有**独立滚动条**，外层消息列表的 `scrollIntoView` 不会带动它，用户看到的是思考过程中间一段。
- 新增 `frontend/src/pencil/components/chat/ReasoningContent.vue`：
  * props `text` / `streaming`；`watch(() => props.text)` 只注册 rAF（不读 layout），回调里每帧最多一次 `scrollTop = scrollHeight - clientHeight`，避免把刚修掉的每 delta 强制布局问题带回来；
  * 贴底检测（阈值 24px）：用户上翻回看时暂停跟随，滚回底部自动恢复；暂停且仍在 streaming 时显示「↓ 回到最新」按钮；
  * `onMounted` 滚一次，streaming false→true 时重置跟随，`onBeforeUnmount` 取消挂起 rAF。
- `ChatMessage.vue`：reasoning 的 `<p>` 替换为 `<ReasoningContent :text :streaming="part.state === 'streaming'">` 并 import 新组件。
- `frontend/src/components.d.ts` 由 unplugin-vue-components 自动生成追加 `ReasoningContent` 全局声明（dev server 产物，非手写，提交时一并带上）。
- 类型检查：`pnpm --filter frontend typecheck:pencil` grep ChatMessage / ReasoningContent 无错误。

## 根因确认 + 自动滚动误判修复

- **用户验证：改 ChatPanel 后「思考卡住」和「此页面没有响应」都解决了** → 根因确认为生成期流式渲染的微任务饥饿（deep watch + 每 delta smooth scroll），字体注册 / WASM / kiwi schema 那一层不是主因，此前的实验 1「空等 30–60s 仍卡」结论一致。字体重复注册可作为独立性能优化，不必再当作本 bug 的根因追查。
- 自动滚动问题：区域高度未达 `max-h-40` 时能跟随，达到固定高度后停止并弹「↓ 回到最新」。
  * 原因：`onScroll` 用 `scrollHeight - scrollTop - clientHeight <= 24` 推断用户是否上翻，但 `scrollHeight` 随 reasoning 内容持续增长；程序自己触发的（延迟派发的）scroll 事件因此被误判成用户上翻 → `following=false` → 停止跟随 + 按钮出现。
  * 修复（`ReasoningContent.vue`）：新增 `lastAutoTop` 记录程序 rAF 写入的精确 scrollTop；`following=true` 时只有 `top < lastAutoTop - 2` 才判定为用户上翻；`following=false` 时仅靠贴底判定恢复；`resume()` 与 streaming 重启时把 `lastAutoTop` 重置为 -1，避免跨轮次旧值误判。
  * 仍保留 rAF 每帧一次布局读写，不回退性能修复。
- 三个改动文件经 `typecheck:pencil` 过滤均无类型错误。
